# CC-1098: o CrowdSec bloqueando o IP de casa

> "temos como previnir que isso nao aconteca mais ou criar alguma coisa que nos
> ajude a resolver mais rapido? muito chato isso"
> (08/11/2026)

Escolha dele, na mesma conversa: **evitar na origem, e o aviso com botão como
reserva**.

## O que é cada coisa

- **CrowdSec:** programa de segurança instalado na VPS. Lê os registros (SSH,
  site) e bloqueia por algumas horas o IP que se comporta como ataque.
- **Cenário:** cada regra de comportamento do CrowdSec. A que pegou ele foi
  `crowdsecurity/http-crawl-non_statics`: um IP pedindo muitos endereços
  diferentes do site (que não são imagem, estilo ou script) em pouco tempo.
- **Exceção (whitelist):** arquivo do CrowdSec que diz quais acessos não contam
  para nenhum cenário.

## O que foi medido em 08/11

1. De casa (IP `200.195.5.197`) a porta 22 dava tempo esgotado; pelo 4G do
   telefone (`179.242.30.67`) o SSH entrava.
2. `tcpdump` na VPS: os pedidos de conexão de casa chegavam (`In ... Flags [S]`)
   e nenhuma resposta saía.
3. `ipset`: o IP estava em `crowdsec-blacklists-1` (`timeout 12296`, cerca de
   3h25). A regra `CROWDSEC_CHAIN ... "CrowdSec: crowdsec" -j DROP` descarta tudo
   dessa lista. `crowdsec`, e não `CAPI`: bloqueio decidido pela própria VPS.
4. `cscli alerts list --ip 200.195.5.197`: **dois bloqueios pelo mesmo cenário**,
   `http-crawl-non_statics`, em 03/11 21:18Z e 08/11 03:10Z (00:10 de Brasília).
5. Registro do nginx (`/var/log/nginx/access.log`, só de 08/11 a partir de
   00:00:29, porque o arquivo vira a cada dia): de 00:05 a 00:10:59 o IP fez
   **219 pedidos, 137 deles no minuto 00:10, em 71 endereços diferentes**.
   Todos com o navegador Chrome (`Chrome/157.0.0.0`), nenhum do painel do PC.
   Mais pedidos: `/api/maquina` (25), `/api/cockpit2` (21), e dezenas de
   `/api/videos/<id>`, um endereço diferente por vídeo.
6. fail2ban: só duas linhas `Found` em 04/11, nenhum bloqueio. Não é ele.

**Causa:** o Cockpit aberto no navegador. A tela que lista vídeos pede um
endereço diferente por vídeo, e somado ao resto das telas passa do limite do
cenário. O painel do PC não aparece nessa janela (ele estava travado nesse
horário, medido em 07/11).

### P1: rascunho da exceção (ele revisa e cola como root)

```yaml
name: carzo/cockpit-api-whitelist
description: "chamadas do Cockpit com login nao contam como varredura"
whitelist:
  reason: "Cockpit /api respondido com sucesso"
  expression:
    - evt.Meta.http_path startsWith '/api/' && evt.Meta.http_status in ['200', '304']
```

Depois: `systemctl reload crowdsec`. O registro do nginx não traz o nome do site
na linha, então a exceção vale para `/api/` de qualquer site da VPS. Aceito
porque exige resposta de sucesso; conferir se outro site da VPS serve `/api/`
sem login antes de colar.

### P2: por que um script, e não liberar o `cscli` direto

A permissão com `cscli decisions delete --ip *` aceitaria qualquer texto no
lugar do `*`, inclusive `--all`, que apaga todos os bloqueios da VPS. O script
recebe só `listar` ou `desbloquear <IP>`, confere o IP e só então chama o
`cscli`.

```sh
#!/bin/sh
# /usr/local/sbin/cockpit-crowdsec : só listar e desbloquear um IP
set -eu
case "${1:-}" in
  listar) exec /usr/bin/cscli decisions list -o json ;;
  desbloquear)
    ip="${2:-}"
    printf '%s' "$ip" | grep -Eq '^([0-9]{1,3}\.){3}[0-9]{1,3}$|^[0-9a-fA-F:]{2,39}$' || { echo "ip invalido" >&2; exit 2; }
    exec /usr/bin/cscli decisions delete --ip "$ip" ;;
  *) echo "uso: cockpit-crowdsec listar | desbloquear <ip>" >&2; exit 2 ;;
esac
```

```
claudedev ALL=(root) NOPASSWD: /usr/local/sbin/cockpit-crowdsec
```

## Riscos

- Quem tomar o `claudedev` consegue se desbloquear. Não apaga os outros
  bloqueios, por causa do script.
- A exceção do P1 deixa de contar `/api/` respondido com sucesso em qualquer
  site da VPS.
